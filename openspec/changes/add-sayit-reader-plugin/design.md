# Design

> **评审草案，尚未冻结。** 技术方向依赖下方标明的产品负责人决策；本文件不授权开始实现。

## Context

See `proposal.md` for the product intent and the three delta specs for observable behavior.

当前应用由 `src/App.tsx` 管理主要输入、检索结果、会话上下文和历史；检索调用 `/api/retrieve`，该路由目前由 Vite 开发服务器配置提供。当前代码没有 Reader、文章收集调度或阅读进度存储。成功的 SayIt 检索进入 `sayit.history.v1`；已保存表达进入独立的 `sayit.saved.v1`。两者均不含 Reader 文章全文和阅读位置。

文本选择可使用浏览器 DOM Selection/Range API。当前 SayIt 主操作会更新主工作区状态，因此 Reader 上下文查询不能未经隔离就直接复用主界面的状态更新处理器。浏览器后台页面的定时器可能受节流，计划时间触发需要在应用重新可见时再校验。

## Goals / Non-Goals

**Goals:**

- 给出可选 Reader 与既有 SayIt 主工作区并存的状态边界，避免上下文查询污染原会话。
- 定义动态发现、原文核验、全文提取、去重、整理、来源归属与失败信息之间的技术流水线。
- 定义只依赖已打开 SayIt 页面运行的调度生命周期、本地文章归档和阅读进度边界。
- 把来源提供商、内容保留策略和日运行语义等产品决策显式提交评审。

**Non-Goals:**

- 本阶段不实现代码、不接入服务、不创建服务凭据，也不声称已有生产级文章发现后端。
- 不在本设计中选定商业搜索供应商、承诺其覆盖率或成本，也不把某个 RSS 清单当作完整发现系统。
- 不在尚未确定内容访问和保留政策前承诺可抓取、存档或离线分发任意出版物的全文。

## Decisions

### Reader 模式与 SayIt 状态隔离

建议在现有应用根状态中增加 Reader 模式，而不是卸载再重新挂载整个 `App`。Reader 入口切换模式视图；主输入、结果、上下文和偏好继续由现有状态持有。文章内 SayIt 调用走同一检索服务和共享结果 contract，但把所选文本作为独立请求参数，并在 Reader 的上下文结果面板中展示，不能直接覆写主工作区输入或结果。

这样既能复用现有检索和结果渲染能力，也能满足 PAT-RM-05 / PAT-RH-04 的状态恢复。备选方案是离开 Reader 时序列化整个主会话再还原；它扩大了状态同步面，容易漏掉新增的临时状态，故不作为首选。

### 发现与文章核验使用服务端适配层

建议由受控服务端适配层负责动态候选发现、原文获取和敏感凭据。前端只请求 SayIt 自己的收集接口，不直接持有搜索服务密钥。当前 `/api/retrieve` 是 Vite 开发服务器路由，不能据此推断 Reader 已有可用的生产服务端；正式实现前必须选定托管位置、凭据管理方式、提供商和预算。

候选流水线建议为：动态主题查询 → 解析并保留原始出版 URL / canonical 提示 → 获取原文页面 → 提取标题、正文、语言、出版者和时间等元数据 → 检查正文是否可读及是否只是摘要/登录页 → URL 与正文相似度去重 → 按主题、难度与阅读时间整理 → 保存带实际来源的结果。RSS 可补充候选，不作为唯一来源。`Mozilla Readability` 可协助提取正文，但其文档明确说明可读性判断只是启发式，可能误判；因此提取成功不能单独证明全文完整。必须保留核验失败原因，且只在替换文章自身通过核验后才将其计作交付。

备选方案是把搜索结果标题/摘要直接当文章交付；这不符合全文阅读意图，也无法满足 PAT-RC-08。若原文无法读取，只显示未核验状态或以另一篇有自己来源信息的文章替换，不得复制候选来源归属。

### 收集生命周期在打开的 SayIt 页面内

建议由页面生命周期管理自动任务：Reader 启用后，启动时读取用户时区的本地日期和当天运行记录；若无已启动尝试则立即补跑。页面仍打开时，可安排用户本地计划时间的检查；页面关闭后不运行任何客户端任务。页面从后台恢复可见时重新计算当前时区日期与计划时间，不依赖后台定时器准点执行。并发启动、启动检查与计划时间检查应使用同一运行锁，先持久化尝试记录，再发出请求，避免同一天重复启动自动任务。

本草案建议任何已启动的自动或手动尝试（包括失败）都抑制当天后续自动运行；失败显示重试/Manual Run now。该规则是产品建议而非已冻结契约。它优先防止启动循环和重复成本。另一个可选规则是失败后在下一次打开时自动重试，或按计划时间而不是首次打开决定补跑；产品负责人需在评审时选择。

打开时立即补跑意味着：如果用户在计划时间之前打开 SayIt，当天收集会提前发生，并抑制稍后的计划运行。这遵从新增的“当天没运行则打开时运行”要求，但会让计划时间更像应用持续打开时的兜底触发点。此语义需明确确认。

### 阅读数据与交互历史分开保存

建议将 Reader 的日期集合、文章元数据、文章正文（若内容政策允许）、来源 URL、预计时长、阅读状态和位置保存在独立的 Reader 数据库；大体量全文优先考虑 IndexedDB，偏好和轻量调度索引可沿用本地存储。为已有数据使用单独版本化命名空间，不写入 `sayit.history.v1` 或 `sayit.saved.v1` 的结构。

Reader 中成功完成的 SayIt 查询仍走现有交互历史仓库，满足用户“像原本 SayIt 一样”的查询历史诉求；文章归档和阅读进度则保存在 Reader 历史。是否还要让查询历史项回链到文章，及文章全文的保留期限/删除入口，需要产品负责人确定。离线展示历史全文依赖正文确实被允许并已存入本地。

备选方案是把文章塞入查询历史，或让查询历史承担阅读进度。这两种方案混合了不同实体和生命周期，不便于按日期恢复文章，也会破坏当前历史格式。

### 文章选择和阅读位置恢复

Reader 通过浏览器当前 Selection 获取非空选择文本，并读取选择范围的矩形来放置轻量上下文操作。执行查询前应复制选中文本为不可变请求值，不能因按钮获得焦点而依赖实时选择仍然存在。无选择时不发起调用。打开结果期间保留同一文章视图与滚动容器；关闭结果时恢复该容器的位置。页面/文章切换时再保存当前进度。

此方案使用普通 DOM 阅读文本，无需把文章变成不可选的 canvas 或图像。`selectionchange` 在 Document 上触发但不会冒泡，选择范围也可能为空；因此需直接检查 selection/range 状态。目标浏览器和触摸/键盘操作覆盖尚待产品负责人确认。

### 内容呈现与来源归属

文章视图从 Reader 自己存储的纯文本/受清理后的 HTML 渲染，不执行出版页面脚本、不加载其原始页面作为嵌入式应用。界面始终显示实际交付文章的标题、出版来源和原文链接；若替换，所有展示和归档字段均来自替换文章本身。非完整或未核验候选不可进入“成功全文”数量统计。

HTML 清理、外部图片与链接的加载方式，以及全文本地保留时长需要在内容访问政策确认后定稿。可读性和难度、阅读时长估算也应记录为估计值，不能呈现为来源方保证的精确属性。

## Risks / Trade-offs

- [缺少生产级发现服务、凭据或稳定来源配额] → 在产品负责人批准来源成本与服务部署边界前，不承诺覆盖率；实现前做供应商/服务可行性选型。
- [网站结构、登录墙、付费墙和地区访问会导致提取不完整] → 将不完整候选标成未核验，允许更换候选，并把失败原因留给用户查看。
- [可读性提取器会误判页面正文] → 组合语言/正文长度/元数据/片段特征检查与人工可观察失败状态；不把单一提取结果等同全文核验。
- [文章全文的本地副本涉及内容访问和保留政策] → PO/产品法务策略确认前，不固定全文缓存范围、保留期或离线可用承诺。
- [浏览器后台定时器会延迟] → 每次启动和页面回到可见状态时重新校验时区日期、计划时间和运行记录。
- [Reader 调用复用全局状态会覆盖已有会话] → 使用独立上下文结果呈现边界，并以 PAT-RM-05、PAT-RH-04 检查往返状态。
- [原有保存能力可能因结果类型而不同] → 当前已知 Save 入口用于检索结果；产品负责人需决定解释型结果是否也要支持 Save。

## Migration Plan

在产品负责人确认契约之前不开始实现。获批后，按新能力逐步增加独立 Reader 存储与功能门控；现有 `sayit.history.v1` 和 `sayit.saved.v1` 数据不需迁移。回滚时关闭 Reader 入口并保留/提供 Reader 本地数据清除策略，不修改现有 SayIt 历史记录。由于尚未选择生产服务端和供应商，部署与回滚细节须在服务方案获批后补全。

## Product Owner Decisions Before Freeze

以下决定会改变验收口径或实现方式，当前均未冻结：

1. Reader 的默认状态是关闭还是首次启动时引导启用。
2. 自动收集在 Reader 插件已启用时运行，还是必须当前正显示 Reader 界面；是否接受“当天首次打开立即补跑，即使早于计划时间；该尝试抑制当天计划任务”的建议；SayIt 打开是指页面已加载还是页面处于前台可见状态。
3. 自动日限额按“已启动尝试”还是“成功/部分完成集合”计算；手动运行是否抑制后续自动运行；失败后是否在下次打开自动重试。
4. “当天”的分界、时区变更与夏令时切换采用何种规则。
5. 每日篇数、总阅读时间、难度和全文核验条件冲突时优先满足哪一项；文章时长/难度用什么可观察算法表示；不足目标时是否接受部分清单及替换提示。
6. 英文文章是否仅限英文原文，是否接受自动翻译后的英文内容；主题来源多样性与同一稿件的转载/联合发布如何去重。
7. 批准的发现/全文服务、部署位置、凭据、成本上限、覆盖范围和离线/故障责任。
8. Reader 历史是否本地保存全文以支持离线；保存期限、清理入口和内容访问政策；用户所说的“历史像原本 SayIt 一样”是否由“Reader 文章归档 + 成功查询进入 SayIt 原历史”满足；查询是否需要关联回文章。
9. 目标浏览器、鼠标/触屏/键盘选择体验、阅读位置按滚动像素还是段落锚点恢复，以及跨重载/设备的保留范围。
10. Save 是否仅对现有支持的检索结果提供，还是需要为解释型结果扩展保存能力。
